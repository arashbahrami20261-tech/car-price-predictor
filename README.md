# Car Price Predictor

A production-style machine learning service that estimates the market price of a
second-hand car. The project covers the full path from raw data to a running
HTTP API: cleaning, training, evaluation, model serving, input validation,
tests, containerisation and continuous integration.

Built by **Arash Bahrami** — [GitHub](https://github.com/arashbahrami20261-tech)

---

## Why this project exists

Most portfolio ML projects stop at a notebook with an accuracy score. That is
model *building*, not model *engineering*. This repository is deliberately built
the other way round: the notebook work is compressed into a single reproducible
training script, and the rest of the effort goes into everything that has to be
true before a model is useful to anyone else.

| Concern | How it is handled |
|---|---|
| Reproducibility | Fixed random seeds, pinned dependency versions, one-command training |
| Training/serving skew | All preprocessing lives inside the scikit-learn `Pipeline` that gets serialised |
| Dirty input data | Duplicates, missing values, inconsistent casing and impossible mileage are handled explicitly |
| Bad API requests | Pydantic rejects them with a `422` before the model is ever called |
| Unseen categories | `OneHotEncoder(handle_unknown="ignore")` instead of a crash |
| Cold-start latency | Model is loaded once at startup via a FastAPI lifespan handler |
| Regressions | Seven pytest checks, run automatically on every push |

## Results

| Metric | Value |
|---|---|
| MAE | 52.3 million toman |
| RMSE | 90.9 million toman |
| R² (held-out test set) | 0.975 |
| R² (5-fold cross-validation) | 0.971 ± 0.003 |

The gap between the cross-validation score and the test score is small, which
suggests the result is not an artefact of one lucky train/test split.

## A note on the data

**The dataset is synthetic.** It is generated by `data/generate_data.py` rather
than scraped from a listings site, so that anyone can clone the repository and
reproduce the exact numbers above without a scraper, an API key, or a licence
question.

The generator is not a toy. It models depreciation as an exponential decay on
vehicle age, applies separate multipliers for body condition, transmission,
fuel type, colour and ownership history, and then adds irreducible market
noise. It also injects the failure modes of real scraped data on purpose:

- ~6% missing mileage values and ~4% missing body-condition values
- inconsistent category casing and stray whitespace
- data-entry errors where kilometres were typed as metres
- exact duplicate rows

Because the underlying relationship is generated, the R² above is higher than
what the same pipeline would achieve on real listings. The engineering is the
deliverable here, not the score. Swapping in a real CSV with the same column
names requires no code changes.

## Running it

```bash
git clone https://github.com/arashbahrami20261-tech/car-price-predictor.git
cd car-price-predictor

python -m venv venv
source venv/bin/activate          # Windows: venv\Scripts\activate
pip install -r requirements.txt

python data/generate_data.py      # Build the dataset
python src/train.py               # Train and save models/model.pkl
uvicorn src.api:app --reload      # Serve at http://127.0.0.1:8000
```

Interactive API documentation is generated automatically at
`http://127.0.0.1:8000/docs`.

### With Docker

```bash
docker build -t car-price-predictor .
docker run -p 8000:8000 car-price-predictor
```

### Tests

```bash
pytest -q
```

## API

| Endpoint | Method | Purpose |
|---|---|---|
| `/health` | GET | Liveness probe for orchestrators |
| `/model-info` | GET | Training timestamp, metrics, accepted categories |
| `/predict` | POST | Price estimate for one car |
| `/docs` | GET | Interactive OpenAPI documentation |

**Example request**

```bash
curl -X POST http://127.0.0.1:8000/predict \
  -H "Content-Type: application/json" \
  -d '{
    "model": "peugeot 206",
    "year": 2018,
    "mileage_km": 120000,
    "engine_size_l": 1.4,
    "fuel_type": "petrol",
    "transmission": "manual",
    "body_condition": "intact",
    "color": "white",
    "previous_owners": 2
  }'
```

**Example response**

```json
{
  "predicted_price_million_toman": 428.8,
  "currency": "IRR (million toman)",
  "model_version": "2026-08-27T19:47:48Z"
}
```

## Modelling choices

**Random Forest.** The relationship between price and the features is not
linear — depreciation curves bend, and body condition interacts with model
tier. A random forest captures those interactions without manual feature
engineering, is insensitive to feature scaling, and is hard to overfit badly
with sensible leaf sizes. Linear regression was the baseline; it lost clearly
on the same split.

**MAE as the headline metric.** It is expressed in the same unit as the target,
so "the estimate is off by about 52 million toman on average" is a sentence a
non-technical user can act on. RMSE is reported alongside it because it
penalises large misses more heavily, and the gap between the two indicates how
often the model is badly wrong rather than mildly wrong.

**Row cleaning outside the pipeline, column cleaning inside it.** Dropping
duplicates and discarding impossible mileage are decisions about which rows
should exist, and they belong before the train/test split. Imputation and
encoding are learned from the training data and must be replayed identically at
prediction time, so they live inside the serialised pipeline.

## Known limitations

- Synthetic data caps how much the reported accuracy says about real listings.
- No hyperparameter search; the current settings are reasonable defaults.
- No monitoring or drift detection — the natural next step for this project.
- Single-model serving with no A/B or shadow deployment path.
